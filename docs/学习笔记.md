## 常用注解速查

这部分只记录项目中已经实际出现过的注解。后续每引入一个新注解，就继续补充。

### `@SpringBootApplication`

使用位置：Spring Boot启动类。

```java
@SpringBootApplication
public class DamaiLearningApplication {
}
```

主要作用：

- 标记Spring Boot应用入口
- 启用自动配置
- 扫描启动类所在包及其子包中的Spring组件

记忆：**启动、自动配置、组件扫描。**

常见问题：启动类位置过深，可能导致其他包中的Controller或Service无法被扫描。

### `@RestController`

使用位置：提供HTTP接口的类。

```java
@RestController
public class HelloController {
}
```

作用：让Spring管理当前类，并把方法返回值直接写入HTTP响应。

可以理解为：

```text
@Controller + @ResponseBody
```

记忆：**这个类提供JSON或文本接口。**

### `@RequestMapping`

使用位置：Controller类或方法。

```java
@RequestMapping("/api")
```

作用：设置请求路径。放在类上时，作为当前类所有接口的公共路径前缀。

记忆：**公共路径。**

### `@GetMapping`

使用位置：Controller方法。

```java
@GetMapping("/hello")
```

作用：把HTTP GET请求映射到Java方法。

当前项目的完整路径：

```text
@RequestMapping("/api") + @GetMapping("/hello")
= GET /api/hello
```

记忆：**查询通常使用GET。**

### `@SpringBootTest`

使用位置：测试类。

```java
@SpringBootTest
class DamaiLearningApplicationTests {
}
```

作用：测试时启动完整的Spring应用上下文，适合验证Spring配置和组件能否正确加载。

记忆：**带着Spring容器运行测试。**

### `@AutoConfigureMockMvc`

使用位置：Spring Boot测试类。

作用：自动配置`MockMvc`，使测试代码可以在不真正启动网络端口的情况下模拟HTTP请求。

记忆：**测试Controller接口。**

### `@Autowired`

使用位置：字段、构造方法或Setter方法。

```java
@Autowired
private MockMvc mockMvc;
```

作用：从Spring容器中找到匹配的对象并注入。

当前代码用它注入测试需要的`MockMvc`。

记忆：**从Spring容器拿对象。**

工程代码中更推荐构造方法注入；这里暂时保留简单写法，后面学习Service时再比较不同注入方式。

### `@Test`

使用位置：JUnit测试方法。

```java
@Test
void contextLoads() {
}
```

作用：标记一个可以由JUnit执行的测试方法。

注意：它属于JUnit，不属于Spring。

记忆：**这是一个自动化测试。**

## Git提交规范速查

项目使用“英文类型前缀 + 中文说明”的提交格式：

```text
<类型>: <本次修改的中文说明>
```

例如：

```text
feat: 添加统一响应结果
```

### 常用提交类型

| 前缀 | 使用场景 | 示例 |
| --- | --- | --- |
| `feat` | 新增功能 | `feat: 添加用户注册功能` |
| `fix` | 修复问题 | `fix: 修复库存重复扣减问题` |
| `docs` | 修改文档 | `docs: 补充Redis学习笔记` |
| `refactor` | 重构代码，但不改变原有功能 | `refactor: 重构订单创建流程` |
| `test` | 增加或修改测试 | `test: 添加节目查询接口测试` |
| `chore` | 构建、配置、依赖等杂项 | `chore: 调整Maven构建配置` |

### 如何选择前缀

```text
增加了用户能够使用的新能力？
→ feat

修正了错误行为？
→ fix

只修改说明文档或学习笔记？
→ docs

代码结构发生变化，但对外行为不变？
→ refactor

只增加或修改测试？
→ test

依赖、构建、工具配置发生变化？
→ chore
```

### 提交说明的要求

- 使用中文描述具体做了什么
- 尽量只描述一个主题
- 避免使用“修改代码”“更新项目”等模糊说明
- 提交前先确认测试通过
- 不在提交说明中包含密码、Token等敏感信息

推荐：

```text
feat: 添加节目分页查询接口
```

不推荐：

```text
更新代码
修改一下
fix bug
```

### 相关命令

```powershell
git add .
git commit -m "feat: 添加统一响应结果"
git push
```

- `git add .`：将当前项目的变更放入暂存区
- `git commit -m "..."`：将暂存区内容保存为一次本地提交
- `git push`：将本地提交推送到远程仓库

## V1：统一响应与接口文档

### 统一响应Result

原始接口直接返回字符串，不同接口很容易形成不同的响应结构。项目增加`Result<T>`，把响应统一为：

```json
{
  "code": 0,
  "message": "success",
  "data": "damai-learning is running"
}
```

三个字段的职责：

- `code`：业务状态码，当前约定`0`表示成功
- `message`：本次请求的结果说明
- `data`：真正的业务数据，类型由泛型`T`决定

常见类型：

```java
Result<String>
Result<UserVO>
Result<List<UserVO>>
```

当前已经同时支持成功响应和基于统一错误码创建失败响应。业务异常和全局异常处理将在下一阶段加入。

### Result的关键设计

```java
private Result(int code, String message, T data)
```

构造方法使用`private`，限制其他代码随意创建不同格式的响应。

```java
public static <T> Result<T> success(T data)
```

通过静态工厂方法统一创建成功响应。

Getter不仅供Java代码读取字段，也方便Jackson把对象转换成JSON。

### 接口自动生成的真正条件

项目引入Springdoc后，它会扫描Spring MVC接口并生成OpenAPI描述。

真正定义接口的是Spring MVC注解：

- `@RestController`
- `@RequestMapping`
- `@GetMapping`
- 后续还会使用`@PostMapping`、`@PutMapping`、`@DeleteMapping`

`@Tag`和`@Operation`不是自动发现接口的必要条件。删除它们以后，接口仍然会生成，只是文档名称和说明不够友好。

### OpenAPI地址

```text
http://localhost:8080/v3/api-docs
```

返回给程序读取的JSON接口定义，Apifox导入这个地址。

```text
http://localhost:8080/swagger-ui.html
```

返回给人查看和调试的Swagger UI网页。这个网页内部仍然需要读取`/v3/api-docs`。

### Apifox同步方式

- 手动导入：接口发生变化后重新导入`/v3/api-docs`
- 定时导入：在项目设置中绑定OpenAPI数据源
- 使用本地URL同步时，Spring Boot应用必须正在运行

### 当前测试策略

- 普通CRUD和展示接口：主要使用Apifox手动验证
- 应用基础状态：保留`contextLoads`测试
- 登录、下单、库存、支付和消息消费：编写自动化测试
- 不要求每个小改动都同时执行手动调用和自动化测试

来源：Swagger/OpenAPI注解。

```java
@Tag(name = "基础接口")
```

作用：给一组接口设置文档分组名称。

记忆：**给Controller分类。**

## V2：统一错误码

### 为什么需要统一错误码

如果每个地方直接写数字和提示语，很容易出现同一种错误使用不同编号、同一个编号表达不同含义的问题。

项目把错误码约束为统一结构：

```java
public interface ErrorCode {

    int getCode();

    String getMessage();
}
```

`ErrorCode`只规定一个错误码必须能够提供`code`和`message`，不关心它具体由哪个枚举实现。以后可以继续增加用户、订单、库存等模块自己的错误码枚举。

### 通用错误码枚举

```java
public enum CommonErrorCode implements ErrorCode {

    INVALID_PARAMETER(40001, "请求参数错误"),
    INTERNAL_SERVER_ERROR(50000, "系统异常");

    private final int code;
    private final String message;

    CommonErrorCode(int code, String message) {
        this.code = code;
        this.message = message;
    }
}
```

当前约定：

- `40001`：请求参数错误
- `50000`：系统内部异常
- 这些是业务状态码，不等同于HTTP状态码`400`和`500`

### 枚举速记

`enum`可以理解为“实例数量固定的特殊类”。普通类可以在外部不断`new`对象，枚举的对象则提前写在枚举内部。

```java
public enum OrderStatus {
    PENDING,
    PAID,
    CANCELLED
}
```

使用时直接选择固定值：

```java
OrderStatus status = OrderStatus.PAID;
```

带字段的枚举仍然可以拥有构造方法、成员变量和方法：

```java
INVALID_PARAMETER(40001, "请求参数错误")
```

这行会调用枚举内部的构造方法，创建一个同时保存错误编号和提示语的固定对象。

需要记住：

- 枚举常量必须写在最前面
- 后面还有字段或方法时，最后一个枚举常量后写分号
- 枚举构造方法不写`public`，不能在外部随意`new`
- 枚举值可以直接使用`==`比较
- 一组互相关联的固定值适合使用枚举；单独一个固定数字或字符串仍可使用常量

### 接口与枚举如何配合

```text
ErrorCode接口
    ↑ 规定必须有code和message
CommonErrorCode枚举
    ↑ 实现这个规定并保存固定错误项
Result.failure(ErrorCode)
    ↑ 接收任何符合规定的错误码
```

因此`Result`不需要依赖某一个具体枚举：

```java
public static <T> Result<T> failure(ErrorCode errorCode) {
    return new Result<>(
            errorCode.getCode(),
            errorCode.getMessage(),
            null
    );
}
```

## V3：业务异常

### 为什么不在Service中直接返回Result

`Result`属于接口响应格式，而Service负责业务逻辑。如果Service也到处返回`Result`，业务层就会和HTTP接口层绑在一起。

更清晰的职责划分是：

```text
Controller：接收请求、返回Result
Service：执行业务规则
业务不允许继续：Service抛出BusinessException
全局异常处理器：捕获异常并转换成Result
```

### BusinessException

```java
public class BusinessException extends RuntimeException {

    private final ErrorCode errorCode;

    public BusinessException(ErrorCode errorCode) {
        super(errorCode.getMessage());
        this.errorCode = errorCode;
    }

    public ErrorCode getErrorCode() {
        return errorCode;
    }
}
```

使用方式：

```java
throw new BusinessException(CommonErrorCode.INVALID_PARAMETER);
```

这行代码表示当前业务流程无法继续，立即抛出一个包含错误码和错误提示的异常。

### Java关键字速记

#### `extends`

```java
BusinessException extends RuntimeException
```

表示`BusinessException`继承`RuntimeException`，因此它本身也是一个运行时异常。

#### `super(...)`

```java
super(errorCode.getMessage());
```

表示调用父类构造方法，把错误提示保存到异常对象中。之后可以通过`exception.getMessage()`读取。

#### `throw`

```java
throw new BusinessException(...);
```

表示主动抛出一个异常对象，并停止当前正常执行流程。注意`throw`用于真正抛出异常，`throws`用于写在方法声明上说明可能抛出的异常，两者含义不同。

#### `final`成员变量

```java
private final ErrorCode errorCode;
```

表示该字段必须在创建对象时完成赋值，并且之后不能重新指向其他错误码，适合保存异常创建时已经确定的信息。

### 为什么继承RuntimeException

`RuntimeException`属于非受检异常，调用业务方法时不需要在每一层强制编写`try-catch`或`throws`。业务异常会继续向上抛出，最后交给统一的异常处理器。

这里先记住结论：业务异常通常继承`RuntimeException`。后面学习Spring事务时，还会看到它与事务回滚的关系。

## V4：全局异常处理

### 为什么需要统一捕获异常

Controller和Service不需要在每个方法中重复编写`try-catch`。业务代码只负责在不满足规则时抛出异常，全局异常处理器负责把异常转换成统一响应。

```text
Apifox发送请求
→ HelloController
→ 抛出BusinessException
→ GlobalExceptionHandler捕获
→ 读取异常中的ErrorCode
→ Result.failure(...)
→ 返回统一JSON
```

### `@RestControllerAdvice`

使用位置：全局异常处理类。

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
}
```

作用：让Spring管理这个类，并让它能够为所有`@RestController`统一处理异常。

记忆：**所有Controller共用的异常处理器。**

### `@ExceptionHandler`

使用位置：异常处理方法。

```java
@ExceptionHandler(BusinessException.class)
```

作用：指定当前方法负责处理哪种异常。

项目现在的处理规则：

```text
BusinessException
→ 返回异常中保存的具体业务错误码

其他Exception
→ 返回INTERNAL_SERVER_ERROR
```

更具体的`BusinessException`由专用方法处理，`Exception`作为最后的系统异常兜底。

### 为什么系统异常需要日志

```java
private static final Logger log =
        LoggerFactory.getLogger(GlobalExceptionHandler.class);
```

```java
log.error("系统发生未处理异常", exception);
```

系统异常不能把内部堆栈直接返回给用户，否则可能泄露代码和运行环境信息。但是开发人员仍然需要通过服务端日志定位异常发生的位置。

当前日志使用Spring Boot自带的SLF4J日志接口，不需要额外添加依赖。

### Result<Void>

失败响应没有正常业务数据，因此异常处理方法使用：

```java
Result<Void>
```

`Void`表示响应中的`data`没有具体数据类型，最终JSON中的值为`null`。

### HTTP状态码与业务状态码

当前接口可能表现为：

```text
HTTP状态码：200
业务状态码：40001
业务提示：请求参数错误
```

HTTP状态码表示这次HTTP通信的结果，业务状态码表示票务业务处理结果。当前学习项目先采用固定响应结构，通过响应体中的`code`判断业务是否成功；后面需要时再学习如何同时设置不同的HTTP状态码。

### 临时异常演示接口

```text
GET /api/hello/error
```

它用于验证`BusinessException`到统一错误响应的完整流程。它不是实际业务接口，等项目拥有真实业务异常场景后会删除。

预期响应：

```json
{
  "code": 40001,
  "message": "请求参数错误",
  "data": null
}
```

## V5：统一请求参数校验

### 为什么需要参数校验

客户端传入的数据不能直接进入业务逻辑。例如姓名为空、手机号格式错误、购买数量小于1，都应该在进入Service之前被拦截。

项目引入：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
```

该依赖的版本由Spring Boot统一管理，因此不需要单独填写`version`。

### DTO是什么

DTO是Data Transfer Object，用来接收或传递一组数据。例如：

```json
{
  "name": "张三"
}
```

可以转换为：

```java
public class HelloRequest {
    private String name;
}
```

请求DTO只描述本次接口允许接收哪些字段，不等同于数据库实体。以后创建节目、创建订单等接口都会有各自的请求DTO。

### `@PostMapping`

```java
@PostMapping("/hello")
```

作用：把HTTP POST请求映射到Java方法。GET和POST可以使用相同路径，因为HTTP请求方式也是接口标识的一部分。

```text
GET  /api/hello
POST /api/hello
```

记忆：**新增数据或提交复杂请求通常使用POST。**

### `@RequestBody`

```java
public Result<String> hello(@RequestBody HelloRequest request)
```

作用：读取HTTP请求体中的JSON，并转换成指定的Java对象。

```text
JSON请求体
→ Jackson反序列化
→ HelloRequest对象
```

记忆：**把JSON请求体转换成Java对象。**

### `@Valid`

```java
public Result<String> hello(
        @Valid @RequestBody HelloRequest request
)
```

作用：要求Spring执行`HelloRequest`字段上声明的校验规则。只写`@NotBlank`等字段规则但不写`@Valid`，Controller参数校验不会自动触发。

记忆：**启动这个请求对象的字段校验。**

### `@NotBlank`

```java
@NotBlank(message = "姓名不能为空")
```

用于字符串，不能是`null`、空字符串或只包含空格的字符串。

与`@NotNull`的区别：`@NotNull`只禁止`null`，仍然允许`""`和`"   "`。

### `@Size`

```java
@Size(max = 20, message = "姓名长度不能超过20个字符")
```

限制字符串、集合等数据的长度或元素数量。这里要求姓名长度最多为20。

Spring Boot 3使用`jakarta.validation`包，不使用旧教程中的`javax.validation`包。

### 参数校验异常处理

参数校验失败后，Controller方法不会继续执行，Spring会抛出：

```java
MethodArgumentNotValidException
```

全局异常处理器取得字段错误：

```java
List<FieldError> fieldErrors =
        exception.getBindingResult().getFieldErrors();
```

当前项目返回第一个字段错误的提示：

```java
String message = fieldErrors.get(0).getDefaultMessage();
```

完整流程：

```text
收到JSON请求
→ @RequestBody转换为HelloRequest
→ @Valid执行字段校验
→ 校验成功：进入Controller方法
→ 校验失败：抛出MethodArgumentNotValidException
→ GlobalExceptionHandler捕获
→ 返回业务码40001和具体字段提示
```

### 方法重载

`Result`现在有两个同名的失败方法：

```java
failure(ErrorCode errorCode)
failure(ErrorCode errorCode, String message)
```

方法名相同、参数列表不同，称为方法重载。Java会根据调用时传入的参数选择对应方法。

第一个方法使用错误码的默认提示，第二个方法允许参数校验返回更具体的字段提示。

### SQL初始化文件

InnoDB支持事务、行级锁和崩溃恢复，是普通Java业务表最常用的MySQL存储引擎。

### 真实业务异常

当前节目不存在时，Service主动抛出：

```java
throw new BusinessException(
        CommonErrorCode.PROGRAM_NOT_EXIST
);
```

全局异常处理器捕获后返回：

```json
{
  "code": 41001,
  "message": "节目不存在",
  "data": null
}
```

学习项目当前继续使用集中的`CommonErrorCode`，与大麦项目使用集中基础错误码的方向保持一致。等错误码明显增多时，再考虑按业务模块拆分，避免现在过度设计。

### 为什么缺少id会变成系统异常

接口映射是：

```text
/api/program/detail/{id}
```

访问`/api/program/detail`时，因为路径缺少`id`，请求不会进入Controller，更不会执行Service中的节目不存在判断。Spring找不到匹配的接口地址，会产生`NoResourceFoundException`。

原来的全局异常处理器没有单独处理它，所以它被最后的`Exception`兜底处理器捕获，错误地显示为“系统异常”。这说明兜底异常处理只能作为最后防线，常见的客户端请求错误仍要单独分类。

当前异常分类：

| 场景 | Spring或业务异常 | 返回结果 |
| --- | --- | --- |
| 请求体违反`@Valid`规则 | `MethodArgumentNotValidException` | `40001`和具体字段提示 |
| 路径参数类型错误，如`id=abc` | `MethodArgumentTypeMismatchException` | `40001 请求参数格式错误` |
| 请求路径不存在或不完整 | `NoResourceFoundException` | `40400 请求地址不存在` |
| 节目不存在、已下架或已删除 | `BusinessException` | `41001 节目不存在` |
| 未预料到的程序故障 | 其他`Exception` | `50000 系统异常`，同时记录日志 |

Spring会优先选择能够匹配具体异常类型的`@ExceptionHandler`方法，只有没有更具体的处理方法时，才会进入`Exception`兜底方法。

### 参数校验与数据库约束为什么都需要

参数校验用于尽早拦截错误，并返回容易理解的提示：


```sql

```

两层职责：

```text
接口参数校验：尽早失败、提示友好
数据库约束：最后防线、保护所有数据写入来源
```


### MyBatis-Plus的`insert`

```java

```

`ProgramMapper`继承了`BaseMapper<Program>`，所以普通单表新增不需要再编写Mapper方法或XML SQL。


## V9：节目分页查询

### 为什么需要分页

一次查询整张表会让数据库读取、网络传输和JVM内存占用随着数据量不断增加。分页让一次请求只处理当前需要的一小部分数据。

基本参数：

```text
pageNum：第几页，从1开始
pageSize：每页多少条
```

MySQL分页位置计算：

```text
offset = (pageNum - 1) × pageSize
```

例如第2页、每页10条：

```sql
LIMIT 10, 10
```

标准分页通常包含两次查询：

```text
COUNT查询：统计满足条件的总记录数
LIMIT查询：取得当前页的数据
```

前端根据`total`、`pageSize`和当前页数据展示页码和翻页按钮。

### PageHelper与MyBatis-Plus分页

PageHelper和MyBatis-Plus分页都很常见：

```text
原生MyBatis或已有老项目：常见PageHelper
已经使用MyBatis-Plus：优先使用Page、IPage和分页拦截器
```

当前项目已经使用MyBatis-Plus，不再重复引入PageHelper。大麦Pro的MySQL分页同样配置了`PaginationInnerInterceptor`并使用`IPage`；它也在部分Elasticsearch结果封装中使用`PageInfo`。同一个项目可能兼容多种分页结果，但具体数据库查询不需要同时套用两套分页插件。

### 分页插件依赖

项目使用MyBatis-Plus 3.5.18。3.5.9以后SQL解析插件被拆成可选模块，因此分页需要额外引入：

```xml
<dependency>
    <groupId>com.baomidou</groupId>
    <artifactId>mybatis-plus-jsqlparser</artifactId>
    <version>3.5.18</version>
</dependency>
```

它负责解析并改写SQL，使普通查询能够生成`COUNT`和`LIMIT`分页SQL。

### 分页配置类

```java
@Configuration
public class MybatisPlusConfig {

    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor =
                new MybatisPlusInterceptor();

        PaginationInnerInterceptor paginationInterceptor =
                new PaginationInnerInterceptor(DbType.MYSQL);

        interceptor.addInnerInterceptor(paginationInterceptor);
        return interceptor;
    }
}
```

执行关系：

```text
MybatisPlusInterceptor：MyBatis-Plus插件总入口
└─ PaginationInnerInterceptor：实际处理分页
   └─ DbType.MYSQL：使用MySQL分页语法
```

### 为什么存在配置类

配置类的本质是告诉Spring：项目启动时应该创建哪些对象，以及这些对象应该如何组装。

Spring管理的对象称为Bean：

```text
Spring容器
├─ ProgramController
├─ ProgramService
├─ ProgramMapper代理对象
├─ DataSource
└─ MybatisPlusInterceptor
```

自己编写的业务类可以直接使用`@Service`、`@RestController`等注解，让Spring扫描并创建对象。`MybatisPlusInterceptor`属于第三方库，不能修改它的源码添加Spring注解，因此使用配置类中的`@Bean`明确创建并交给Spring。

启动过程：

```text
Spring扫描到MybatisPlusConfig
→ 识别@Configuration
→ 调用带有@Bean的方法
→ 得到MybatisPlusInterceptor对象
→ 注册到Spring容器
→ MyBatis-Plus把它加入SQL执行流程
```

如果只在Service中直接`new MybatisPlusInterceptor()`，它只是Service内部的普通对象，并不会自动进入MyBatis的SQL执行链。

### `@Configuration`

```java
@Configuration
```

作用：标记一个Spring Java配置类，通常用于组装项目基础设施。

记忆：**这个类告诉Spring怎样配置组件。**

### `@Bean`

```java

```

作用：把方法返回的对象注册到Spring容器。方法名默认也是Bean名称。

记忆：**把这个方法创建的对象交给Spring。**

### `application.yml`与配置类

```text
application.yml：主要提供端口、地址、用户名等配置数据
@Configuration：主要创建对象并定义对象之间如何组合
```

Spring Boot已经根据依赖和`application.yml`自动创建了DataSource、SqlSessionFactory等对象，所以之前不需要自己编写数据库配置类。分页插件不是默认开启的，需要项目明确选择数据库类型并把插件加入执行链，因此增加自定义配置类。

### 前端编辑为什么需要先查询

正常编辑是两次独立HTTP请求：

```text
GET详情
```

### `LambdaUpdateWrapper`

`LambdaUpdateWrapper<Program>`是更新SQL构造器，不是数据库记录对象。

三个核心方法：

```text
eq：构造WHERE等于条件
set：构造SET更新内容
update：真正执行SQL
```

当前代码：

```java
updateWrapper
        .eq(Program::getId, id)
        .eq(Program::getStatus, 1)
        .set(Program::getTitle, request.getTitle())
        .set(Program::getActor, request.getActor())
        .set(Program::getPlace, request.getPlace())
        .set(
                Program::getItemPicture,
                request.getItemPicture()
        );
```

大致对应：

```sql
UPDATE d_program
SET title = ?,
    actor = ?,
    place = ?,
    item_picture = ?
WHERE id = ?
  AND status = 1;
```

`Program::getTitle`是方法引用，MyBatis-Plus据此识别`Program`的`title`属性；`itemPicture`根据下划线转驼峰配置对应数据库的`item_picture`。

执行：

```java
programMapper.update(null, updateWrapper);
```

`update`的第一个参数可以提供Entity中的更新字段。当前所有`SET`都已写在Wrapper中，因此第一个参数传`null`；这不表示没有更新内容。

### 为什么不使用查询出来的完整Entity更新

完整Entity包含标题之外的字段：

```text
programStatus
status
createTime
editTime
```

如果请求A先读取完整对象，请求B随后把节目下架，请求A再用旧完整对象修改标题，就可能把旧的`programStatus=1`重新写回，意外覆盖请求B的`programStatus=0`。

只在UPDATE中设置当前接口允许修改的字段，可以避免修改标题时顺便覆盖上下架状态、数据状态和时间字段。数据库仍可通过`ON UPDATE CURRENT_TIMESTAMP`维护`edit_time`。

### `affectedRows`

```java
int affectedRows =
        programMapper.update(null, updateWrapper);
```

它表示UPDATE匹配或影响的记录数：

```text
1：匹配到目标有效节目，更新成功
0：记录不存在或status已经不是1，没有记录被修改
```

检查`affectedRows`不是“修改错了以后补救”。数据库先根据WHERE匹配记录，再决定是否更新；匹配不到时不会修改数据。

### 并发问题分类

#### Lost Update：更新丢失

两个请求读取旧状态后分别提交，后提交的内容覆盖先提交的内容，导致先提交的更新消失。

#### Stale Write：陈旧写入

请求使用之前读取的旧Entity写回数据库。例如另一个请求已经下架节目，当前请求仍把旧的`programStatus=1`写回。陈旧写入可能导致更新丢失。

#### Last Write Wins：最后写入者获胜

它描述系统表现：没有版本控制时，后提交的更新通常成为最终结果。它可能造成Lost Update。

#### Check-Then-Act / TOCTOU：检查与执行竞态

```text
SELECT检查status=1
→ 其他请求把status改成0
→ 当前请求继续UPDATE
```

检查时和使用时状态不同。把`status=1`直接放进同一条UPDATE的WHERE条件，可以让数据库原子地完成条件检查和修改，消除这段时间窗口。

### 当前更新方案解决范围

| 问题 | 是否解决 | 方式 |
| --- | --- | --- |
| 修改标题时覆盖别人刚改的上下架状态 | 是 | UPDATE只包含允许字段 |
| 先检查有效，随后记录被逻辑删除 | 是 | `status=1`直接放入UPDATE条件 |
| 记录不存在 | 是 | `affectedRows=0`并抛业务异常 |
| 两个人同时修改同一个标题 | 否 | 后续需要version乐观锁 |
| 前端长时间打开表单后提交旧内容 | 未完全解决 | 后续需要version乐观锁 |

只添加`@Transactional`不能自动解决同字段更新丢失；通常需要版本号乐观锁，或在确实需要串行执行时使用悲观锁。

### 下架、逻辑删除和物理删除

```text
programStatus：节目能不能卖
status：这条数据是否还参与正常业务
```

状态组合：

| programStatus | status | 含义 |
| ---: | ---: | --- |
| 1 | 1 | 正常上架 |
| 0 | 1 | 已下架，可编辑或重新上架 |
| 0 | 0 | 已逻辑删除 |

下架不是删除。下架节目可能修改后重新销售，也需要保留订单、售票和运营历史。

逻辑删除：

```sql
UPDATE d_program
SET status = 0
WHERE id = ?;
```

物理删除：

```sql
DELETE FROM d_program
WHERE id = ?;
```

逻辑删除保留记录，适合节目、订单、支付等重要业务数据，但所有正常查询和更新都必须过滤`status=1`。物理删除后普通UPDATE确实匹配不到记录，可以消除“修改逻辑删除记录”这一具体问题，但不能解决两个请求同时编辑同一字段造成的Lost Update。

票务核心数据常使用逻辑删除，主要原因是历史订单关联、误删恢复、运营统计和审计，而不是为了避免并发问题。临时数据、缓存数据或确定没有历史价值的数据可以根据业务使用物理删除。

```java
        .eq(Program::getStatus, 1)
        .eq(Program::getProgramStatus, 1)
        .set(Program::getProgramStatus, 0);
```

大致对应：

```sql
UPDATE d_program
SET program_status = 0
WHERE id = ?
  AND status = 1
  AND program_status = 1;
```

条件含义：

```text
id匹配：找到指定节目
status=1：节目没有被逻辑删除
program_status=1：节目当前确实处于上架状态
```

不存在、已逻辑删除或已下架时，WHERE匹配不到记录，返回：

```text
41002 节目不存在或已下架
```

### 下架接口为什么不先查询

单条条件UPDATE让数据库原子完成：

```text
检查节目存在
检查数据有效
检查当前已上架
修改为下架
```

它比“先SELECT、Java判断、再UPDATE”少一次数据库访问，也避免两条SQL之间状态变化产生的TOCTOU竞态。

### 下架后的业务表现

下架只产生：

```text

status：仍然为1
```

因此：

- 公开详情查询不到，因为公开详情要求`programStatus=1`
- 公开分页列表不再包含该节目
- 数据库记录仍然存在
- 后台编辑仍然允许，因为编辑只要求`status=1`
- 将来可以增加重新上架操作

## V13：空值缓存与缓存穿透

### 什么是缓存穿透

如果客户端反复查询数据库中不存在的节目：

```text
请求不存在的id
→ Redis没有缓存
→ 查询MySQL
→ MySQL也没有数据
→ 返回节目不存在
```

因为不存在的数据无法按照正常节目JSON写入缓存，下一次相同请求仍会访问MySQL。大量请求持续绕过Redis访问数据库，这种情况叫缓存穿透。

### 为什么使用特殊字符串

Redis中Key不存在通常表示“还没有缓存”，但业务还需要表达另一种状态：

```text
这个id已经查询过，并且MySQL中确定不存在
```

因此项目约定使用一个普通字符串作为标记：

```java
private static final String NULL_CACHE_VALUE =
        "__NULL__";
```

`"__NULL__"`不是Java的`null`，只是项目自己约定的普通字符串。

三种读取结果分别表示：

```text
Redis返回null
→ Key不存在，属于真正的缓存未命中
→ 继续查询MySQL

Redis返回"__NULL__"
→ 以前已经查询过，节目不存在
→ 直接返回业务异常，不再查询MySQL

Redis返回JSON
→ 正常节目缓存命中
→ 反序列化成ProgramDetailVO并返回
```

### 空值缓存流程

第一次查询不存在的节目：

```text
Redis未命中
→ 查询MySQL
→ MySQL确认不存在
→ Redis写入"__NULL__"
→ 返回节目不存在
```

第二次查询相同节目：

```text
Redis读取到"__NULL__"
→ 直接返回节目不存在
→ 不访问MySQL
```

### 为什么空值缓存时间更短

```java
private static final Duration NULL_CACHE_TTL =
        Duration.ofMinutes(2);
```

正常节目详情缓存10分钟，空值缓存只保存2分钟。空值过期时间较短，可以减少“数据库后来出现了数据，但Redis仍然认为数据不存在”的时间窗口。

### 相关Redis命令

```powershell

```

删除旧Key，保证从缓存未命中开始测试。

```powershell

```

查看缓存内容，空值缓存应为`"__NULL__"`。

```powershell

```

查看剩余过期秒数，刚写入时应接近120秒。

## V14：Redis故障降级

### 为什么缓存异常不能拖垮查询接口

节目真实数据保存在MySQL中，Redis只是加速层。如果Redis暂时不可用，详情查询仍可以回退到MySQL：

```text
读取Redis失败
→ 记录WARN日志
→ 按照缓存未命中处理
→ 查询MySQL
→ 返回节目详情
```

Redis恢复前，请求会变慢并增加MySQL压力，但核心查询功能仍然可用。这种降低性能、保留核心功能的处理叫故障降级。

### 为什么捕获DataAccessException

```java
catch (DataAccessException exception)
```

Spring会把Redis连接、命令执行等数据访问异常转换成`DataAccessException`的子类。捕获它比捕获所有`RuntimeException`更准确，不会顺便隐藏其他程序错误。

### 读取失败如何触发回源

读取Redis失败时，缓存方法返回Java的`null`：

```text
返回Java null
→ 表示没有得到可用缓存
→ Service继续查询MySQL
```

这和Redis中的特殊字符串`"__NULL__"`不同：

```text
Java null：缓存不可用或Key不存在，需要查询MySQL
"__NULL__"：已经确认节目不存在，不查询MySQL
```

### 写入缓存失败为什么可以忽略

如果MySQL已经查询成功，只是把结果写入Redis失败：

```text
MySQL数据可用
→ 记录WARN日志
→ 忽略本次缓存写入失败
→ 把节目详情返回给客户端
```

代价是后续请求可能继续查询MySQL，但不应该因此把一次成功的MySQL查询变成系统异常。空值缓存写入失败也采用相同原则，仍然返回原本的“节目不存在”业务异常。

### Windows Redis与Docker Redis端口冲突

本机还安装了Windows Redis服务，并设置为自动启动：

## V15：事务保护写操作与缓存删除

### 没有事务时的半完成问题

编辑和下架采用：

```text
更新MySQL
→ 删除Redis缓存
```

如果没有事务，MySQL更新通常会立即提交。随后Redis删除失败时，接口虽然返回系统异常，但数据库实际上已经修改：

```text
MySQL：已经修改
接口：返回失败
Redis：仍是旧缓存
```

这会让调用方误以为整个操作失败，并且造成数据库与缓存不一致。

### Service事务边界

编辑和下架方法增加：

```java
@Transactional
```

事务放在Service业务方法上，因为一个业务操作同时包含更新数据库、检查影响行数和删除缓存。Controller只负责接收请求，Mapper只负责执行SQL，都不适合作为完整业务事务边界。

### 正常执行流程

```text
开启MySQL事务
→ 执行UPDATE
→ 删除Redis缓存成功
→ Service方法正常结束
→ COMMIT提交MySQL事务
```

### Redis删除失败时

```text
开启MySQL事务
→ 执行UPDATE，但尚未提交
→ 删除Redis失败并抛出DataAccessException
→ Service方法异常结束
→ ROLLBACK回滚MySQL事务
```

最终结果：

```text
MySQL仍是旧数据
Redis仍是旧缓存
接口返回失败
```

操作虽然没有成功，但数据库与缓存保持一致，也不会出现“接口说失败，数据库却已经修改”的情况。

### Redis删除成功但MySQL提交失败

`@Transactional`只管理MySQL事务，不能回滚Redis命令。如果Redis已经删除、MySQL随后提交失败：

```text
MySQL回滚为旧数据
Redis缓存不存在
```

下一次查询会从MySQL读取正确的旧数据并重建缓存。缓存缺失只会暂时降低性能，不会返回错误数据。

### 为什么不需要事务配置类

项目已经配置数据源并使用MyBatis-Plus，Spring Boot会自动准备数据库事务管理器。`@Transactional`声明业务方法需要事务，不需要手动调用`commit()`或`rollback()`，也不需要为当前场景额外编写配置类。

### 当前验证状态

- 编辑和下架方法已添加`@Transactional`
- Redis停止时编辑操作返回失败
- Redis删除异常会使MySQL更新回滚
- DataGrip验证数据库仍为修改前的数据

## V17：查询节目场次和票档

### Entity、Mapper和VO

场次与票档分别创建Entity和Mapper：

```text

```

MyBatis-Plus通过`map-underscore-to-camel-case`完成`program_id → programId`等字段映射，通过`@TableName`明确带`d_`前缀的真实表名。

```text

└─ List<TicketCategoryVO>
```

Entity保留数据库完整字段，VO只暴露前端需要的场次、时间、票价和可用库存。

### 嵌套响应

接口：

```http
GET /api/program/{programId}/sessions
```

一个`ProgramSessionVO`内部包含当前场次的`ticketCategories`，从而形成“场次下面包含票档”的嵌套JSON结构。

### 为什么先校验节目

直接查询场次并返回空列表，无法区分以下两种情况：

```text
节目存在，但暂时没有场次
节目本身不存在或已经下架
```

因此Service先校验节目存在、未删除且已上架。节目有效但没有场次时返回成功空列表；节目无效时返回`PROGRAM_NOT_EXIST`业务异常。

### 避免N+1查询

不在场次循环中逐个查询票档。先查询全部场次id，再通过`IN`一次查询全部票档：

```text
查询场次：1次SQL
批量查询票档：1次SQL
总计：2次SQL
```

如果循环查询10个场次的票档，将产生1次场次查询和10次票档查询，这种随数据量增长而增加SQL次数的问题叫N+1查询。

### groupingBy分组

批量查询得到的是平面票档列表，通过：

```java
Collectors.groupingBy(TicketCategory::getSessionId)
```

转换成：

```text
场次id → 该场次的票档列表
```

最终类型为：

```java
Map<Long, List<TicketCategory>>
```

组装每个场次VO时，根据场次id从Map中取出票档列表，不需要再次访问数据库。

## V18：MyBatis-Plus、自定义SQL与下单事务

### 当前下单流程仍然在使用MyBatis-Plus

```java
ticketCategoryMapper.selectById(...);
programSessionMapper.selectById(...);
programMapper.selectById(...);
ticketOrderMapper.insert(...);
```

这些通用查询和插入来自MyBatis-Plus的`BaseMapper`。只有原子扣库存使用Mapper XML中的自定义SQL。

### 为什么扣库存使用自定义SQL

库存扣减需要数据库在一条SQL中同时完成：

```text
检查库存是否充足
检查票档是否可售
扣减可用库存
```

核心表达式是：

```sql
available_stock = available_stock - #{quantity}
```

并且需要条件：

```sql
available_stock >= #{quantity}
```

MyBatis-Plus也可以通过`LambdaUpdateWrapper`和`setSql()`拼出类似SQL，但这已经超出普通`updateById()`的通用CRUD范围。库存是核心业务，显式XML更容易阅读、审查和确认最终执行的SQL。

### 为什么不能读取旧库存后updateById

两个请求可能同时读取到库存1：

```text
请求A读取1
请求B读取1
请求A计算并写入0
请求B也计算并写入0
```

两个请求都认为扣减成功，但实际只减少了一张库存。自定义条件UPDATE让数据库在执行更新时基于当时的真实库存判断，`affectedRows`才是最终结果。

### 事务不是按照表数量决定

下单虽然只修改一条票档库存并插入一条订单，但实际包含两条写SQL、两张表：

```text
UPDATE d_ticket_category
INSERT d_order
```

是否需要事务取决于这些操作是否必须共同成功，而不是取决于操作几张表。即使同一张表连续执行两条必须共同成功的SQL，也可能需要事务。

### 抛异常不等于自动撤销SQL

没有事务时，数据库通常会分别自动提交每条SQL：

```text
UPDATE库存成功并提交
→ INSERT订单失败
→ Java抛异常并返回系统错误
→ 已提交的库存不会自动恢复
```

添加`@Transactional`后：

```text
BEGIN
→ UPDATE库存，暂未提交
→ INSERT订单失败
→ 抛出运行时异常
→ ROLLBACK
→ 库存恢复
```

错误响应负责告诉调用方结果，数据库事务才负责恢复数据状态，两者不是同一件事。

## V19：简化下单与事务回滚验证

### 创建订单接口流程

```text

→ 查询并校验票档

```

请求只接收`userId`、`ticketCategoryId`和`quantity`。节目id、场次id、真实单价和总金额全部由后端查询或计算。

### @Positive

`@Positive`要求数字大于0，但允许`null`，所以id字段同时使用：

```java
@NotNull
@Positive
```

`@NotNull`负责不能为空，`@Positive`负责传入值必须为正数。购买数量具有明确上下限，因此使用`@Min(1)`和`@Max(6)`。

### 售票时间校验

```text
当前时间早于saleStartTime：尚未开售
当前时间晚于saleEndTime：已经停售
其他情况：处于售票时间
```

时间校验、状态校验和库存条件共同决定票档是否可以下单。

### 订单状态枚举

`OrderStatus`在Java中表达待支付、已支付和已取消，数据库仍保存整数状态码。业务代码使用`OrderStatus.PENDING_PAYMENT.getCode()`，避免直接出现难以理解的数字1。

### 订单号

当前使用`DM + UUID`生成订单号，并通过数据库唯一索引`uk_order_no`最终保证订单号不重复。后续需要有序分布式id时再学习雪花算法，不在当前阶段过度设计。

```text
第二次请求没有造成库存减少
```

这证明`@Transactional`在订单插入异常时回滚了前面的库存UPDATE。实验结束后已经恢复UUID订单号生成逻辑。

### Objects.equals与提前返回

订单状态字段是`Integer`包装类型，使用：

```java
Objects.equals(orderStatus, expectedStatus)
```

可以安全比较值，即使`orderStatus`为`null`也不会抛出空指针异常。不使用`==`比较两个包装类型引用。

取消订单通过提前返回区分状态：

```text
已取消：return，方法立即结束
不是待支付：抛出业务异常
待支付：两个条件都不进入，继续执行取消
```

前面的`return`使已取消订单不会继续进入后面的通用异常分支。

只保留“不是待支付就抛异常”的第二个判断，也不会重复恢复库存，因此从数据库最终状态看同样具有幂等效果。增加第一个判断的区别在于接口语义：重复取消一个已取消订单时返回成功，而不是返回状态错误。这更适合客户端因超时或响应丢失而自动重试。

## V20：取消订单、恢复库存与状态条件

### 取消流程

```text
根据userId和orderNo查询订单
→ 已取消：直接返回成功
→ 非待支付：拒绝取消
→ 条件更新为已取消
→ 恢复票档库存
→ 提交事务
```

### 为什么同时使用userId和orderNo

订单号是对外业务标识，但不是授权凭证。取消时仍要校验订单属于当前用户。当前`userId`暂时由请求传入，接入登录后必须改为从登录上下文获取。

### 状态条件更新

修改订单状态时，UPDATE条件继续限制`order_status = 待支付`。即使Service查询时订单还是待支付，执行UPDATE前也可能被其他请求改变状态，最终结果必须以数据库更新时的状态为准。

```text
updatedRows = 1：本次请求真正完成状态变化
updatedRows = 0：状态已经变化或订单不满足条件
```

只有状态修改成功的请求才能继续恢复库存，从而避免并发取消导致库存被多次增加。

### 恢复库存的上限保护

恢复库存SQL增加：

```sql
available_stock + quantity <= total_stock
```

避免程序异常时把可用库存恢复到总库存以上。XML中小于号需要转义，因此写成`&lt;=`。

### 取消事务

订单状态修改和库存恢复必须共同成功。如果恢复库存失败，事务回滚订单状态，避免订单已经取消但库存没有恢复。

### 当前验证状态

- 待支付订单可以取消
- 取消后订单状态变为已取消
- 库存按照订单数量恢复
- 重复取消返回成功但不重复恢复库存
- 错误用户无法取消不属于自己的订单
- 已支付等非待支付状态不允许取消
