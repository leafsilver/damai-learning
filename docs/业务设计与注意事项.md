# 大麦学习项目：业务设计与注意事项

本文只记录本项目开发过程中实际遇到的业务设计、风险和工程决策。Java语法、注解用法和命令说明仍记录在《学习笔记》中。

## 1. 不信任客户端传入的业务结果

### 遇到的场景

创建订单时，前端只需要提交：

```text
userId（接入登录前的临时方案）
ticketCategoryId
quantity
```

以下字段不能直接采用前端传值：

```text
programId
sessionId
unitPrice
totalAmount
orderStatus
```

### 风险

前端页面上的请求可以被用户通过Apifox、浏览器开发者工具或脚本重新构造。如果后端直接相信前端传入的价格，用户可以把真实票价改成很小的金额：

```json
{
  "ticketCategoryId": 1,
  "quantity": 2,
  "unitPrice": 1
}
```

### 项目决策

后端根据`ticketCategoryId`查询数据库中的真实票档，再获取可信的单价、场次id和节目id：

```text
ticketCategoryId
→ 查询票档和真实单价
→ 根据sessionId查询场次
→ 根据programId查询节目
→ 后端计算totalAmount
```

原则：前端传“用户选择了什么”，后端计算并确认“最终业务结果是什么”。

## 2. userId由请求传入只是临时方案

### 当前阶段

项目还没有登录模块，因此创建订单请求暂时包含`userId`，方便先学习订单和库存流程。

### 风险

用户可以修改请求中的`userId`，冒充其他用户下单或查询其他用户的数据。

### 后续决策

接入登录鉴权后，`userId`必须从经过认证的登录上下文中获取，不能继续相信请求体中的用户id。

## 3. Entity、DTO和VO各自控制数据边界

```text
Entity：对应数据库表，不直接作为接口请求或响应
DTO：只接收当前接口允许客户端填写的字段
VO：只返回当前接口需要展示的字段
```

独立DTO可以避免客户端修改`status`、`orderStatus`、`createTime`等内部字段。独立VO可以避免把逻辑删除状态、内部关联字段等数据库细节暴露给前端。

## 4. 金额使用精确类型并保存下单快照

票价和订单金额在MySQL中使用`DECIMAL`，Java中使用`BigDecimal`，不使用可能产生浮点精度误差的`float`或`double`。

订单保存下单时的`unitPrice`和`totalAmount`。即使运营以后修改票档价格，历史订单金额也不能跟着变化。

## 5. 库存不能先查询再扣减

### 错误流程

```text
SELECT查询库存
→ Java判断库存是否足够
→ UPDATE扣减库存
```

并发请求可能同时读取到相同的旧库存，造成超卖。

### 项目决策

使用一条带条件的UPDATE同时完成库存检查和扣减：

```sql
UPDATE d_ticket_category
SET available_stock = available_stock - #{quantity}
WHERE id = #{ticketCategoryId}
  AND available_stock >= #{quantity}
  AND ticket_status = 1
  AND status = 1;
```

`affectedRows = 1`表示扣减成功，`affectedRows = 0`表示库存不足、票档不存在或不可售。

## 6. 扣库存和创建订单必须放在同一个事务

下单包含两个必须共同成功的数据库操作：

```text
扣减票档库存
插入订单记录
```

如果扣库存成功但订单插入失败，事务必须回滚库存；否则会出现库存减少但没有订单的情况。因此下单Service需要使用`@Transactional`覆盖完整流程。

需要特别注意：Java抛异常或接口返回失败，只表示调用方收到了失败结果，不代表数据库会自动撤销之前已经提交的SQL。

没有事务时：

```text
库存UPDATE成功并自动提交
→ 订单INSERT失败
→ 接口返回失败
→ 库存已经减少，但订单不存在
```

有事务时：

```text
开启事务
→ 扣库存但暂不提交
→ 插入订单失败
→ 运行时异常触发回滚
→ 库存恢复
```

是否需要事务取决于多个操作是否必须保持“全部成功或全部失败”，而不是简单按照涉及几张表判断。同一张表上的多条关联写操作也可能需要事务。

### 项目验证

项目通过固定测试订单号制造唯一索引冲突：第一次下单成功，第二次请求先执行库存UPDATE，随后订单INSERT失败。最终库存没有再次减少，并且数据库中仍只有一条订单，证明事务已经回滚库存。

测试结束后已恢复UUID订单号生成逻辑，固定测试值不能提交到正式代码。

## 12. 订单状态变化必须限制来源状态

订单不能从任意状态随意修改到另一个状态。例如取消订单只能允许：

```text
待支付 → 已取消
```

已经支付或已经取消的订单不能再次取消。更新状态时需要把当前状态放进UPDATE条件，而不是先查询状态再无条件`updateById()`。

库存恢复必须和“待支付改为已取消”绑定。只有订单状态真正修改成功的请求才能恢复库存，避免重复取消导致库存被多次增加。

## 13. 对外使用订单号，内部使用数据库主键

`d_order.id`是数据库内部主键，适合表关联和数据库操作；`order_no`是对外业务标识，适合用户订单页、客服查询、支付和取消订单等业务场景。

当前接口使用订单号的原因：

```text
数据库自增id属于内部实现细节
连续id容易被顺序猜测
订单号可以在日志、支付和后续服务之间统一传递
以后分库分表时，订单号比单库自增id更适合作为全局业务标识
```

订单号不是密码，不能仅凭订单号授权操作。取消订单仍然必须同时校验订单所属用户；接入登录后，用户id从登录上下文获取。

## 14. 已取消订单返回成功是一种接口语义选择

取消订单根据当前状态分别处理：

```text
待支付：执行取消并恢复库存
已取消：直接返回成功，不再次恢复库存
已支付等其他状态：拒绝取消
```

只保留“不是待支付就拒绝”的判断，也能保证重复请求不再修改订单或恢复库存，因此从最终状态和副作用看仍然具有幂等效果。第二次请求只是会返回业务错误。

项目把“已取消”单独返回成功，是为了提供更适合网络重试的接口语义：客户端第一次取消可能已经成功，只是响应丢失；再次请求时，服务端发现目标状态已经达成，仍然告诉客户端取消成功。

因此第一个判断不是防止重复恢复库存所必需的，它用于区分两种接口约定：

```text
严格状态校验：已经取消 → 返回状态不允许错误
目标状态语义：已经取消 → 目标已经达成，返回成功
```

## 7. 订单号需要数据库唯一索引兜底

Java负责生成订单号，数据库通过：

```sql
UNIQUE KEY uk_order_no (order_no)
```

保证订单号最终不能重复。应用校验用于正常业务流程，数据库约束用于并发和程序错误下的最终保护。

## 8. 逻辑删除状态和业务状态含义不同

项目中的`status`表示数据是否被逻辑删除；`programStatus`、`sessionStatus`、`ticketStatus`和`orderStatus`表示各自的业务状态。

例如节目下架只修改`programStatus`，不代表这条数据库记录被删除。查询时通常需要同时判断逻辑删除状态和业务状态。

## 9. 批量查询避免N+1问题

查询节目场次和票档时，不在场次循环中逐次查询票档。项目先批量查询场次，再使用场次id集合一次查询全部票档，并通过`groupingBy`按场次分组。

```text
推荐：1次场次SQL + 1次票档SQL
避免：1次场次SQL + N次票档SQL
```

## 10. 缓存是加速层，MySQL是真实数据源

节目详情使用Cache Aside模式。查询时Redis异常可以回退到MySQL；修改节目时先更新MySQL，再删除缓存。

写操作中，数据库更新和缓存删除放在事务控制范围内。缓存删除失败时让数据库更新回滚，避免接口返回失败但数据库已经修改。

节目不存在时使用短期空值缓存，减少不存在id反复访问MySQL造成的缓存穿透。

## 11. 高频变化的库存暂不直接缓存

场次和票档接口当前直接查询MySQL。票价和场次信息相对稳定，但`availableStock`会随着下单频繁变化。如果把整个响应长期缓存，可能向用户展示陈旧库存。

后续引入Redis库存时，需要单独设计库存初始化、扣减、回滚和数据库一致性，不能直接套用节目详情缓存。
